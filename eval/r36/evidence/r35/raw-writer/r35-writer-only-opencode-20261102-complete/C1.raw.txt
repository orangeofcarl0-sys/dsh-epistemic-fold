The user's requirement is a delivery guarantee, not a latency preference, so a backend whose failure mode is silently dropped events is unacceptable regardless of how fast it is. Kernel notification was the default and looked adequate in casual use; the canary deployment on the same platform as the cache client exercised that default and exposed gap-prone delivery, which is why the design moved toward periodic directory scanning. Scan-based detection was chosen because its cost degrades predictably with directory size and interval, whereas notification loss cannot be detected from the notification path itself. A hybrid (watch for fast path, scan to reconcile) was considered and set aside: it still needs a scan interval to bound worst-case staleness, so the watch leg buys little beyond extra state to reason about. Retrying missed watch events was rejected outright — a lost event leaves nothing to retry. Next: pick the interval against the cache client's staleness budget, then land the backend behind the existing interface.
</handoff>
